# 프로그래머 작업 및 코딩 규칙

버전: 1.0  
적용 대상: 프로젝트의 코드·데이터·테스트·빌드 설정을 변경하는 프로그래머 및 AI 작업자

## 1. 목적과 우선순위

이 문서는 언어와 엔진에 독립적인 기본 작업 절차와 코드 작성 규칙을 정의한다.

규칙은 다음 순서로 적용한다.

1. 사용자 또는 책임자의 최신 명시적 지시
2. 저장소의 `AGENTS.md`, `CONTRIBUTING.md` 등 작업자 규칙
3. 승인된 기획·아키텍처·데이터·스타일 명세
4. 이 문서
5. 개인 관행

규칙이 충돌하거나 선택에 따라 결과가 크게 달라지면 임의로 결정하지 않고 책임자에게 보고한다.

## 2. 작업 시작

- 요청의 목표, 허용 범위, 금지 범위, 완료 조건을 확인한다.
- 현재 브랜치, 작업 디렉터리, 변경 파일, untracked 파일, stash를 확인한다.
- 요구사항과 관련 코드의 호출 경로 및 데이터 흐름을 끝까지 추적한다.
- 기존 구현, 표준 라이브러리, 플랫폼 기능, 설치된 의존성 순서로 재사용 가능성을 확인한다.
- 문서나 테스트가 현재 제품 사양과 다르면 제품 코드를 억지로 맞추지 말고 차이를 먼저 보고한다.
- 요구하지 않은 리팩터링, 추상화, 설정, 의존성은 추가하지 않는다.

## 3. 최소 변경 원칙

- 증상이 아니라 모든 관련 호출이 통과하는 공통 원인을 한 번 수정한다.
- 같은 효과라면 수정 파일 수와 코드량이 가장 적은 해법을 선택한다.
- 동작을 바꾸지 않는 정리 작업은 기능 변경과 분리한다.
- 하나의 구현만 있는 interface나 factory, 미래만을 위한 확장점은 만들지 않는다.
- 한 번만 쓰이는 단순 표현을 helper나 wrapper로 감싸지 않는다.
- 파일과 클래스는 실제 책임이 분리될 때만 나눈다.
- 기존 공용 시스템, adapter, manager, 데이터 경로를 우회하지 않는다.
- 임시 코드와 debug 설정은 제품 동작에 영향을 주지 않아야 하며 제거 조건을 기록한다.

## 4. 이름과 함수

- 이름은 역할과 단위를 드러내고 의미 없는 축약어와 타입만 반복하는 이름을 피한다.
- boolean 이름은 참일 때의 의미가 읽히도록 작성한다.
- 시간, 거리, 비율, 화폐처럼 단위가 중요한 값은 이름이나 타입에 단위를 표현한다.
- 매직 넘버는 의미가 반복되거나 조정 대상일 때만 상수로 승격한다.
- 함수는 한 가지 결과를 만들고 이름과 다른 부수 효과를 숨기지 않는다.
- 입력과 출력이 분명한 작은 함수를 우선하되 단순한 흐름을 과도하게 쪼개지 않는다.

## 5. C# 코드 배치와 정리

클래스 구성원은 구성원 종류, 접근 범위, 호출 흐름 순서로 배치한다. 알파벳 자동 정렬보다 관련 동작을 가까이 두는 것을 우선한다.

권장 배치 순서는 다음과 같다.

1. `const`
2. `static`, `static readonly` 필드
3. `[SerializeField] private` 필드
4. 일반 인스턴스 필드
5. 프로퍼티와 indexer
6. event와 delegate
7. 생성자
8. 프레임워크·엔진 생명주기 함수
9. 공개 API
10. `protected` 확장 지점
11. `private` 내부 함수
12. 이벤트·충돌 callback
13. 중첩 타입

같은 구성원 종류 안에서는 특별한 이유가 없으면 `public → protected → internal → private` 순서로 둔다.

- 필드는 기본적으로 `private`로 선언하고 외부 공개가 필요하면 프로퍼티나 명시적인 함수로 제공한다.
- C# 접근 한정자를 생략하지 않는다. 타입과 구성원의 의도를 코드에 명시한다.
- 변경되지 않는 필드는 `readonly`, 컴파일 상수는 `const`를 사용한다.
- 함수는 가능하면 실제 호출 흐름에 따라 위에서 아래로 배치한다.
- overload와 같은 기능의 함수는 서로 붙여 둔다.
- Unity 생명주기 함수는 `Awake → OnEnable → Start → Update → FixedUpdate → LateUpdate → OnDisable → OnDestroy` 순서로 둔다.
- callback은 관련 공개 API 또는 내부 처리 함수와 가까이 둘 수 있으며, 이 경우 일관성을 유지한다.
- `#region`은 큰 파일을 유지하기 위한 수단으로 사용하지 않는다. 파일의 책임을 먼저 점검한다.
- 사용하지 않는 변수, 함수, `using`, 주석 처리된 코드, 의미 없는 주석은 제거한다.
- 변수는 사용하는 위치와 가깝게 선언하고 불필요하게 넓은 scope를 주지 않는다.
- 기존 파일을 수정할 때는 해당 파일의 일관된 스타일을 우선하며, 기능 변경과 무관한 전체 재정렬은 하지 않는다.

## 6. 상태와 수명

- 상태 소유자가 상태 변경과 불변 조건을 함께 책임진다.
- 동일한 상태를 여러 위치에 저장하지 않고 하나를 권위값으로 두며 나머지는 계산한다.
- 전역 상태, singleton, static mutable state는 기존 아키텍처가 요구할 때만 사용한다.
- 전역 상태와 캐시는 소유자, 초기화, 사용, 정리 시점을 명확히 한다.
- 중복 호출과 재진입이 가능한 함수는 멱등성을 보장하거나 명확한 거부 조건을 둔다.
- 이벤트 구독자는 해제 책임을 가진다.

## 7. 입력과 데이터

- 외부 입력, 파일, 네트워크, 사용자 입력은 시스템 경계에서 검증하고 내부에는 검증된 값을 전달한다.
- 식별자·키·라우팅 규칙은 프로젝트의 단일 권위 타입과 범위를 따른다.
- 문자열, 파일명, 표시명, UI 문구를 내부 식별자나 데이터 종류 라우팅에 사용하지 않는다.
- 파싱 결과를 완전히 검증한 뒤 실제 상태를 교체한다.
- 신규 데이터는 PK 중복, FK 존재, 범위, 필수값, 파서·로더 범위, 버전 및 직렬화 호환성을 확인한다.
- 직렬화 형식 변경 시 기존 데이터의 읽기 가능 여부와 migration 방식을 명시한다.

## 8. 오류와 안정성

- null이 정상 상태인지 오류 상태인지 API 계약에 명시한다.
- null, 빈 컬렉션, 중복 호출, 낮은 프레임률, 중단 및 재시도 상황을 고려한다.
- 예외를 삼키거나 성공값으로 바꾸지 않는다.
- 복구 가능한 오류만 현재 계층에서 처리하고 나머지는 문맥을 보존해 전달한다.
- catch 범위는 가능한 좁게 유지한다.
- 실패 중에도 파일, 메모리, lock, 구독, 임시 상태가 정리되도록 한다.
- 부분 갱신이 불일치를 만들면 검증 후 일괄 교체하거나 rollback 가능한 순서를 사용한다.
- 데이터 손실, 보안, 접근성, 복구 가능성을 최소 구현이라는 이유로 생략하지 않는다.

## 9. 비동기, 성능, 프레임 안정성

- fire-and-forget은 실패를 관찰할 책임자가 있을 때만 사용한다.
- 취소 가능한 작업은 cancellation을 전달하고 정상 취소와 오류를 구분한다.
- 객체 제거 뒤 callback, coroutine, task가 상태를 변경하지 않도록 수명을 확인한다.
- 공유 상태의 경쟁 조건과 실행 순서 의존성을 제거한다.
- timeout과 retry는 실제 외부 실패 가능성이 있을 때만 추가하며 무한 재시도하지 않는다.
- 측정 전에 복잡한 최적화나 캐시를 추가하지 않는다.
- 반복 경로에서는 불필요한 할당, 전체 검색, 문자열 조합, 중복 계산을 피한다.
- 시간 기반 로직은 프레임 수가 아닌 경과 시간을 기준으로 한다.
- 낮은 프레임률, 큰 시간 간격, 한 프레임의 다중 이벤트에서도 상태 전이가 누락되지 않아야 한다.
- 물리·충돌·이동은 프로젝트가 정한 고정 시간 루프와 단일 권위 시스템을 따른다.

## 10. 의존성, 주석, 문서

- 새 패키지는 표준 기능과 기존 의존성으로 해결할 수 없을 때만 추가한다.
- 하위 계층이 상위 UI나 구체적인 저장소 구현을 직접 참조하지 않게 한다.
- 순환 참조를 만들지 않는다.
- 코드를 그대로 번역하는 주석은 쓰지 않는다.
- 제약의 이유, 비직관적인 선택, 외부 계약, 알려진 한계만 기록한다.
- TODO에는 적용 조건과 제거 기준을 함께 적는다.
- 공개 API와 데이터 형식 변경 시 관련 명세와 예제를 같은 작업에서 갱신한다.

## 11. Git과 환경 조작

- 사용자의 dirty·untracked 파일과 무관한 변경을 보존한다.
- 승인된 경로만 `git add -- <paths>`로 stage하고 광범위 stage는 하지 않는다.
- commit 전 `git diff --cached --check`, name-status, stat, staged count를 확인한다.
- 생성 자산은 본 파일과 메타데이터·매핑 파일의 짝을 확인한다.
- checkpoint는 로컬 commit이며 push·pull·merge·브랜치 정리는 별도 승인 후 수행한다.
- `reset --hard`, `clean`, 강제 push, 임의 stash, 광범위 포맷팅은 명시적 승인 없이 수행하지 않는다.
- 프로세스 종료, 시스템 종료, 삭제, 배포, 외부 메시지 전송처럼 복구가 어렵거나 외부에 영향을 주는 작업은 명시적 권한을 받는다.
- 재귀 삭제·이동 전 대상의 절대 경로와 작업 영역 포함 여부를 확인한다.
- 비밀값을 명령 출력, 로그, 문서, 커밋에 노출하지 않는다.

## 12. 완료 및 리뷰 체크리스트

- 요청된 기능과 데이터가 실제로 반영됐는가?
- 허용 범위 밖 파일을 수정하거나 요구사항 밖 동작을 추가하지 않았는가?
- 기존 공용 구현을 중복 작성하거나 더 단순한 표준 기능을 놓치지 않았는가?
- 모든 호출자가 같은 수정 경로를 사용하는가?
- 데이터 권위, 실패·취소·정리 경로, 낮은 프레임률과 중복 이벤트가 안전한가?
- 새 의존성이나 추상화가 지금 실제로 필요한가?
- 테스트가 회귀 원인을 직접 검증하며 실행 결과가 명시됐는가?
- 정적 결과와 런타임 결과를 구분했는가?
- 임시 코드와 debug 설정의 제거 또는 유지 결정이 기록됐는가?
- Git 변경, commit, push, merge 여부와 남은 위험 및 후속 승인을 구분했는가?

## 13. 금지 사항

- 사양을 추측해 큰 구조를 변경하기
- 기존 공용 경로를 우회하는 임시 시스템 만들기
- 검증을 약화하거나 예외를 숨겨 테스트만 통과시키기
- UI 문자열·파일명·표시명을 내부 키로 사용하기
- 무관한 코드를 함께 리팩터링·포맷·stage·commit하기
- 사용되지 않는 확장점, wrapper, 설정, 패키지 추가하기
- 정적 성공을 실제 런타임 성공으로 보고하기
- 소유권과 정리 방식이 없는 전역 상태·이벤트·비동기 작업 만들기
- 승인 없이 외부 배포·병합·삭제·강제 종료하기
