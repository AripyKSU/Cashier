# CSV ID와 컬럼 규칙

## 1. 문서 목적

이 문서는 프로젝트에서 사용하는 CSV 데이터의 `idx`, 컬럼 타입, 참조와 스키마 변경 규칙을 정의한다.

모든 CSV 작성자와 작업자는 동일한 ID 구조와 종류별 범위를 사용하여 서로 다른 데이터 테이블 사이의 ID 중복을 방지한다.

## 2. 기본 형식

- `idx`에는 숫자만 사용한다.
- ID는 개념적으로 `CCCIII` 형식의 6자리 숫자로 구성한다.
- 앞의 세 자리 `CCC`는 데이터 종류 ID를 나타낸다.
- 뒤의 세 자리 `III`는 해당 데이터 종류 안에서 사용하는 고유 ID를 나타낸다.
- 하나의 완성된 ID는 `데이터 종류 ID × 1000 + 고유 ID`로 계산한다.

| 구분 | 자리 | 의미 |
|---|---:|---|
| 데이터 종류 ID | 앞 3자리 | CSV 또는 데이터 테이블의 종류 |
| 고유 ID | 뒤 3자리 | 같은 종류 안에서 각 데이터를 구분하는 값 |

CSV에서 ID를 숫자형으로 읽으면 앞쪽의 `0`은 값에 포함되지 않을 수 있다. 예를 들어 `001001`과 `1001`은 같은 숫자 ID로 취급한다. 앞쪽 0은 형식을 읽기 쉽게 표시할 때만 사용하며 별개의 ID를 뜻하지 않는다.

## 3. 데이터 종류 ID

- 데이터 종류마다 서로 다른 세 자리 종류 ID를 배정한다.
- 종류 ID는 `001`부터 `999` 범위에서 사용한다.
- 이미 다른 CSV 또는 데이터 테이블에 배정된 종류 ID를 다시 사용하지 않는다.
- 새로운 CSV 종류를 추가하기 전에 기존 종류 ID와 예약된 범위를 확인한다.
- 배정된 종류 ID는 코드의 `DataTableType` 값 및 로더 분류 규칙과 일치해야 한다.

종류 ID의 실제 배정과 예약 현황은 Google Docs의 [CSV 종류 ID](https://docs.google.com/document/d/1lCzaQRmFRWrxfIhWr2UZy64-7A8v1N9fAvlOorMF77E/edit?pli=1&tab=t.ccpln6m1g4kv) 문서를 단일 권위 목록으로 사용한다.

- 새로운 종류 ID를 배정하거나 기존 배정을 변경할 때는 해당 Google Docs 문서를 갱신한다.
- CSV, `DataTableType` 또는 loader를 구현하기 전에 해당 문서에서 종류 ID의 중복과 예약 여부를 확인한다.
- 저장소의 규칙 문서나 개별 코드 주석에 종류 ID 목록을 별도로 복제하지 않는다.

## 4. 종류별 고유 ID

- 고유 ID는 각 데이터 종류 안에서 `001`부터 `999` 범위로 배정한다.
- 같은 종류 ID 안에서는 동일한 고유 ID를 중복해서 사용할 수 없다.
- 삭제되거나 사용이 중단된 ID는 참조 및 저장 데이터 호환성을 확인하기 전까지 다른 데이터에 재사용하지 않는다.
- 표시명, 파일명 또는 CSV 행 순서를 고유 ID 대신 사용하지 않는다.
- 새로운 ID를 배정하기 전에 대상 종류의 기존 ID와 예약된 ID를 확인한다.

## 5. 작성 및 검증 절차

1. 추가할 데이터가 속한 종류 ID를 확인한다.
2. 해당 종류에서 사용 중이거나 예약된 고유 ID를 확인한다.
3. 종류 ID와 고유 ID를 결합해 `idx`를 작성한다.
4. 같은 CSV 안의 중복과 다른 CSV에 배정된 종류 범위 침범 여부를 검사한다.
5. DTO의 `idx` 자료형, `DataTableType`, parser와 loader routing이 같은 규칙을 사용하는지 확인한다.
6. 병합 직전에 최신 기본 브랜치를 기준으로 ID 중복을 다시 검사한다.

규칙에 맞지 않거나 중복된 ID가 발견되면 해당 CSV를 런타임 데이터로 등록하지 않고 원인을 수정한 뒤 다시 검증한다.

## 6. 컬럼 타입과 문자열 사용

- CSV는 텍스트 파일이지만 각 컬럼의 논리 타입은 명시적으로 정의한다. 숫자를 문자열로 읽어 내부 키나 분기 조건으로 사용하지 않는다.
- 숫자, 숫자 enum 값, boolean, 숫자 ID 또는 숫자 ID 배열을 우선한다. ID와 FK는 프로젝트의 `uint` 계약을 따른다.
- 표시 이름은 `name` 문자열로 중복 저장하지 않고 `nameidx`로 `TextData.idx`를 참조한다. 설명·대사도 필요한 경우 같은 방식으로 명시된 TextData FK를 사용한다.
- 다른 데이터나 리소스를 연결할 때 표시명·파일명·경로 문자열을 복사하지 않고 대상 테이블의 idx를 참조한다. 리소스 경로는 ResourceData에서만 해석한다.
- 문자열은 `ResourceData.path`, `TextData.text`처럼 **해당 컬럼의 용도가 문자열 자체인 경우에만** 허용한다. 새 문자열 컬럼은 사용 목적과 숫자·ID로 대체할 수 없는 이유를 스키마에 기록하고 승인받는다. 기존에 명시적으로 허용된 문자열은 불필요하게 숫자로 바꾸지 않는다.
- enum은 허용된 숫자값과 의미를 명시하고 정의되지 않은 값은 거부한다. boolean은 기존 converter의 `0/1` 계약을 따른다.
- 색상·시간·수량 등은 의미에 맞는 숫자 타입·단위·범위를 정한다. 현재 손님 외형은 색상 열을 사용하지 않고 필수 `image_resource_idx`로 Sprite를 참조한다. 상품의 기본·탑뷰 FK와 빈값 규칙은 [IMAGE_RESOURCE_INTEGRATION.md](IMAGE_RESOURCE_INTEGRATION.md)를 따른다.
- ID 배열은 기존 converter의 `_` 구분 형식을 유지하며 runtime에서는 숫자 ID 배열로 읽는다. 모든 원소의 FK를 검사하고 중복 허용 여부를 명시한다.
- 참조 없음은 스키마에서 허용한 경우에만 사용한다. `0`, 빈 셀, 누락 컬럼은 서로 다른 상태이며 임의로 바꾸거나 같은 기본값으로 처리하지 않는다. 필수 `nameidx`에는 `0`이나 빈 값을 허용하지 않는다.

### 컬럼 명세에 기록할 항목

CSV별 관련 명세에 다음 항목을 기록한다. 이 설명을 CSV의 주석 행이나 추가 데이터 행으로 넣지 않는다.

| 항목 | 기록 내용 |
|---|---|
| 컬럼명·순서 | 실제 header와 순서. `idx`는 첫 컬럼 유지 |
| 타입·의미 | DTO 타입, 의미, 단위 및 enum/boolean 해석 |
| 필수·기본값 | 빈 셀·0 허용 여부, 명시적 기본값의 적용 조건 |
| 허용 범위 | 최솟값·최댓값, 고유성·배열 중복 규칙 |
| 참조 | FK 대상 테이블·컬럼과 필수 존재 조건 |
| 변환 | CsvHelper mapping과 필요한 기존 converter |
| 문자열 예외 | 문자열 컬럼일 때 용도와 허용 근거 |

### 확률 단위: 1000 = 100%

- 신규 확률 컬럼과 계산은 정수 `0~1000`을 사용한다. `0 = 0%`, `1 = 0.1%`, `850 = 85%`, `900 = 90%`, `1000 = 100%`다.
- 컬럼명과 C# 구성원명은 확률의 의미로 작성하고 `permille` 같은 단위 접미사를 요구하지 않는다. `1000 = 100%`는 이 작성 규정과 컬럼 명세·코드 주석에 명시한다. CSV에는 `%` 기호나 소수 문자열을 저장하지 않는다.
- 성공 판정은 균등 정수 난수 `0 이상 1000 미만`에 대해 `난수 < 확률값`으로 계산한다. 0은 항상 실패하고 1000은 항상 성공한다. 범위 밖 입력은 LogError와 예외로 거부하며 임의 clamp하지 않는다.
- UI의 퍼센트 표시는 `확률값 / 10.0`으로 변환한다. 저장값을 정수 나눗셈으로 조기에 축소하지 않는다.
- 상대 가중치는 확률과 구분한다. `*_weight`는 후보 간 비율이며 합계 1000을 강제하지 않는다. 합계 1000인 배타적 확률 분포를 사용하는 경우에만 전체 합계를 검증한다.
- 기존 `0~100` 확률은 자동으로 재해석하지 않는다. 승인된 migration에서 값 × 10, 필요한 컬럼·DTO 이름 정리, 범위 검사·난수 분모·소비자·검사를 함께 변경한다. 이전 값과 새 단위를 혼용하지 않는다.
- 검증에는 경계값 0·1000, 범위 밖 입력 거부, 900의 90% 해석을 포함한다. 유한 횟수 표본이 정확히 90%여야 한다고 요구하지 않는다.

## 7. 기존 데이터와 스키마 변경 보호

1. 수정 전에 실제 header·컬럼 순서·encoding·delimiter, DTO mapping·converter, 로더와 모든 소비자를 확인한다. 종류 ID는 3절의 Google Docs 권위 목록을 확인하며, 접근할 수 없으면 새 배정·변경만 보류한다.
2. 단순 값 수정에서는 기존 컬럼을 삭제·추가·재정렬·rename하거나 타입을 변경하지 않는다. 요청과 무관한 행·PK·FK·빈값도 보존한다.
3. `name → nameidx`, 타입 변경, 컬럼 분리·삭제와 ID 이관은 스키마 migration으로 다룬다. 변경 목적·범위, 이전→새 값 매핑, 영향을 받는 소비자·세이브 및 복구 방법을 먼저 기록하고 승인된 범위에서 진행한다.
4. 원본 또는 되돌릴 수 있는 Git 기준점을 확보한다. 문자열을 TextData로 옮길 때 기존 문구를 누락·변형하지 않는다. 승인된 Text ID를 배정하고 새 FK로 연결하며, 같은 문구라도 의미가 다르면 승인 없이 하나의 ID로 합치지 않는다.
5. CSV, DTO, mapping·converter, 로더, PK·FK 검증, UI 등 소비자, 관련 예제·검사를 같은 작업에서 갱신한다. 컬럼 이름만 바꾸거나 새 테이블에 연결되지 않은 CSV만 만들고 완료로 처리하지 않는다.
6. 새 규칙을 기존 데이터에 적용한다는 이유로 숫자 전체를 일괄 치환하지 않는다. ID 이관은 테이블 종류와 참조 관계를 기준으로 하고, ResourceData.path 같은 허용 문자열·asset GUID·Addressables address는 별도 승인 없이는 바꾸지 않는다.
7. 기존 GUID를 보존하고 asset과 `.meta`를 함께 관리한다. 실패 시 부분 데이터가 활성화되지 않도록 전체 파싱·FK 검증 후 공개한다. 검증되지 않은 기본값·임시 이름·이전 ID 별칭으로 실패를 숨기지 않는다.

## 8. 변경 후 검증

- 변경 전후 행 수·컬럼명·순서·타입과 변경 대상 외 값의 보존을 확인한다. 승인된 행·컬럼 증감은 그 이유를 기록한다.
- PK 고유성·종류 대역·모든 FK와 `nameidx → TextData.text` 조회를 확인한다. 문자열이 명시적 허용 컬럼에만 남아 있는지 검사한다.
- CsvHelper로 실제 파일을 읽어 필수 header, 숫자 변환, enum·boolean·범위·빈값·배열 규칙을 검사한다. 문자열의 쉼표·따옴표·개행은 CSV 규격에 따라 보존하며 수동 Split으로 파싱하지 않는다.
- 누락·잘못된 FK나 필수값은 파일·행/PK·컬럼·대상과 원인을 포함한 LogError와 예외로 보고하고 runtime 공개를 차단한다.
- 영향을 받은 컴파일·최소 실행 경로에서 실제 데이터 조회·표시를 확인한다. 파싱 성공만으로 실행 성공을 보고하지 않는다.
- 공통 완료 상태와 실행 검증 절차는 [`DATA_RULES.md`](DATA_RULES.md) 및 [`WORK_RULES.md`](WORK_RULES.md)를 따른다.
