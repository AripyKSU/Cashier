# 180초 영업의 8·10·12건 처리 구조 점검

2026-09-13, 설비 비용 반영 커밋 `91e3fb5` 기준. **하루10건을 막는 거래 수 상한이나 손님 공급 부족은 확인되지 않았다.** 다만 UI 자동 연출에 건당 약4.15초가 필요하므로10건 목표의18초 주기 중 약13.85초가 상품 조작·계산·가격 제출·결과 확인에 남는다. 실제 사람의 처리 가능 여부를 측정한 결과는 아니다.

## 실제 연결과 시간 예산

MainScene은 GameUI 프리팹의 `useCustomerQueue`를1로 덮어쓴다. 프리팹 원본의0만 읽고 대기열 미사용으로 판단하면 안 된다. 첫 손님은 영업 시작 시 바로 생성·인계하고, 이후에는5초마다 대기열 입장을 시도한다. 대기열 정원10은 현재 계산대 손님을 제외한 동시 대기 정원이며, 하루 성공 거래 상한이 아니다.

| 처리 구간 | 현행 시간 | 근거 |
|---|---:|---|
| 손님 등장 대기 | 0.80초 | GameUI prefab customerArrivalSeconds |
| 상자 내려놓기 | 0.85초 | SaleSortingPanel.playContainerArrival |
| 자동 전환 대기 | 0.50초 | GameUI prefab autoAdvanceDelaySeconds |
| 작업대 전환 | 1.00초 | 프리팹 transitionSeconds; 클래스 기본0.25가 아님 |
| 상품 쏟기 | 0.65초 | GameUI prefab pourSeconds |
| 빈 상자 퇴장 | 0.35초 | SaleSortingPanel.playEntryFlow |
| **분류 입력 시작 전 합계** | **4.15초** | 참조된 버튼·상자·작업대가 있는 현재 프리팹 경로 |

위 합은 설정값과 순차 coroutine 대기를 합한 명목 시간이다. 프레임 경계·성능에 따라 더 길어질 수 있다. 자동 전환 대기는 현재 양수 설정이며, 진행 중 transitionRoutine이 있으면 박스 클릭 handler가 반환하므로0.5초를 자유롭게 생략할 수 있다고 가정하지 않았다.

거래 결과 대사는 마우스/Enter로 확인한다. 무조건 기다려야 하는 별도 결과 표시 타이머는 없다. `CompleteTransactionResult`는 현재 손님을 보내고 바로 다음 손님을 요청한다. 퇴장 표시0.45초는 다음 손님의 등장과 겹치며 매 거래마다4.15초에 다시 더하지 않는다. 마지막 정산 표시에는 퇴장 완료 대기가 적용된다.

| 목표 정가 거래 | 평균 한 주기 | 명목 자동 연출 | 조작·계산·결과 확인에 남는 시간 |
|---|---:|---:|---:|
| 8건 | 22.50초 | 4.15초 | 18.35초 |
| 10건 | 18.00초 | 4.15초 | 13.85초 |
| 12건 | 15.00초 | 4.15초 | 10.85초 |

상품은 현재 성향 데이터에서1~3종·종당1~3개로 최대9개다. 위 남는 시간에 상품 구분/이동, 당일가·지침 확인, 합계 계산, 가격 입력, 결과 확인을 모두 수행해야 한다. 상품 수와 가격 자릿수·지침 수가 실제 처리량을 바꾸므로 이 시간을 사람의 난도로 확정하지 않는다.

## 실제 대기열·거래 API 확인

설치된 Unity CLI 연결을 통해 Unity6000.3.18f1의 `CustomerQueue`, `CustomerGenerator`, `CustomerVisit`를 직접 호출했다. 기존 CSV 파서로 현재15성향·21상품 데이터를 읽고, 시작일 기본 상품으로 새 방문을 생성했다. 각 목표100개 seed, 총300개의 가상 영업일을 실행했다. 0.05초 단위로 실제 Queue.Advance를 호출하면서4.15초를 연출 시간으로 예약하고, 각 주기의 끝0.05초 전에 정확한 정가로 주문 전체를 제출한 뒤 결과를 완료했다.

| 목표 | 완주 실행 | 손님 부족 실행 | 가격 거절 |
|---|---:|---:|---:|
| 8건/180초 | 100/100 | 0 | 0 |
| 10건/180초 | 100/100 | 0 | 0 |
| 12건/180초 | 100/100 | 0 | 0 |

**이 표는 기존 큐가 해당 서비스 주기에 손님을 공급할 수 있다는 확인이다. 실제 화면을 조작한 PlayMode 테스트, 전체 GameProgress의180초 실시간 실행, 이용자 성공확률 검사가 아니다.** 거래 완료를 정해진 시각에 API로 수행했고 UI coroutine은 실행하지 않고 시간만 배정했다. 새 테스트 framework나 제품 코드는 추가하지 않았다.

손님 생성은 기존 생성기의 성향 배열 overload를 사용했다. 메인 게임의 날짜·명성별 선택기를 연결한 경제 모형이 아니며, 이 결과로 이전 시민권 확보 확률이나 평균 객단가를 갱신하지 않는다. 자금·명성 정산·설비 투자·라디오를 합친 재검증도 이번 범위에 포함하지 않았다. 명성별 구성이나 실제 UI 흐름의 검증은 기존 실행/별도 플레이테스트와 구분한다.

## 대기 이탈과 마감의 영향

현행 손님 대기 인내는9·12·15·18초이고 계산대로 넘어온 방문에는 대기열 만료를 적용하지 않는다.5초 입장보다15~22.5초 처리 주기가 느려 대기 이탈은 생길 수 있다. 이번 점검에서도 이탈은 있었지만 다음 손님이 없어10건을 못 채우는 경우는 없었다. 이탈 수를 실제 플레이 예상치로 사용하지 않으며 원시 관찰값은 results.json에만 보존했다.

현재 이탈은 금전·명성 직접 벌칙 없이 통계로 제공된다. 다만 짧은 인내의 손님이 계산대 전에 더 자주 이탈하면 실제로 응대한 성향 비율이 달라질 수 있다. 앞서 시민권 시뮬레이션은 이 선별 효과를 포함하지 않았으므로58.5% 등의 값은 당시 모형 조건부 결과로 남긴다.

시간 만료 후에는 대기열을 비우고 새 손님을 시작하지 않지만 이미 계산대에 있던 마지막 거래는 완료할 수 있다. 이번300개 실행은 가격 제출을180초 전에 끝내도록 구성했고 이 마감 여유에 기대지 않았다. 전체 진행의 마감·마지막 거래 계약은 직전 PlayMode45/45 검증과 코드에서 별도 확인했다.
