# 밸런싱 초안 플레이테스트 — 첫 기록

2026-09-13. 목적은 **현재 UI로 자연스럽게 플레이했을 때 하루 몇 건이 성립하는지** 확인하는 것이다. 우선1~3일차만 진행한 뒤 기록을 검토한다. 31일 시민권 성공률을 검증하거나 특정 거래 수를 억지로 달성하는 시험이 아니다.

## 먼저 할 일

1. 평소 사용하는 실행 경로로 새 게임을 시작한다. 프로젝트 안내의 기본 경로는 InitScene → Hub → MainScene이다. 개인 실험 씬이나 임의 날짜·잔액 변경은 비교 조건으로 사용하지 않는다.
2. 1~3일차를 평소 속도로 플레이한다. 현재가에 맞춘 정가 판매와 지침 준수를 시도하되 실수한 날도 그대로 남긴다.8건을 채웠다고 영업을 멈추거나, 기록을 좋게 만들려고 재시작하지 않는다.
3. 영업 중에는 수기로 세거나 기록하지 않는다. 각 날의 정산 화면에서 **설비 상점에 들어가기 전** 아래 표를 채운다. 다음날로 넘기기 전에 확인한다.
4. 설비를 구매했다면 상품명·가격·구매일을 추가 메모한다. 첫 비교에서는 가능한 경우 식량 선반을 먼저 구매한다.3일차 구매는 경제 목표이며 날짜 해금 조건이 아니다. 돈이 부족하면 기다리고 실제 구매일을 기록한다.
5. 3일차 정산 기록이 끝나면 우선 검토한다. 이 결과로 처리량 가정과 조작상 어려움을 확인한 후 중반·후반 테스트로 넘어간다.

게임 영업시간의 현재 기본값은180초다. 하루3일의 영업 타이머 합은9분이지만 감독관·설비·정산과 마감 뒤 마지막 거래 시간을 포함한 실제 소요 시간은 더 길다. 화면 시계의09:00~21:00 표시는 현실의12시간이나 초 단위 스톱워치가 아니다.

## 복사해서 채울 기록표

실행일: ___ / 새 게임 여부: ___ / 익숙함: 처음·조금 익숙·익숙 / 입력 장치: ___

아래에서 모르는 값은 `미확인`, 화면에 없으면 `미표시`로 적는다. 빈칸이나 미확인을0으로 바꾸지 않는다. 금액은 모두G이며 정산 잔액은 그날 설비를 사기 전 값이다.

어려움은 기억나는 것만 적는다. 예: 상품 구분, 끌어서 놓기, 합계 계산, 가격 입력, 뉴스·지침 확인, 결과 확인, 연출 대기, 조작 실패. 정확한 발생 횟수를 기억하지 못하면 추측해 채우지 않는다.

## 정산 화면에서 읽는 법

| 기록 | 현재 구현의 의미 | 해석 주의 |
|---|---|---|
| Sales | 성립한 판매 수 | 정가뿐 아니라 수락된 할인·폭리도 포함한다. 정가 성공 수로 단정하지 않는다. |
| Refused | 가격 제안이 거절된 손님 수 | 처리 시도에는 포함하지만 수입이 발생한 판매에는 포함하지 않는다. |
| Departed | 대기 중 인내 만료로 이탈한 손님 수 | 계산대에서 거절된 손님과 다르다. 마감 때 대기열을 비운 수와도 다르다. 직접 벌칙은 없다. |
| 총 판매 수입 | SaleIncome | 순익·잔액과 혼동하지 않는다. |
| 지침 벌금 | 정산된 위반 금액 | 화면에서 확인되지 않을 때 지침 개수만 보고 벌금을 추정하지 않는다. |
| 현재 잔액 | 정산 화면의 CurrentBalance | 설비 구매 전/후를 섞지 않는다. 미납이 표시되면 추가 메모한다. |
| 명성 | 크게 상승/상승/변화 없음/하락/크게 하락 문구 | 현재 화면에서 숫자 명성이나 응대한 성급한 손님 수를 필수로 요구하지 않는다. 문구로 정확한 누적 명성을 복원하지 않는다. |

MainScene이 사용하는 GameUI의 중첩 정산 프리팹을 확인했다. SettlementPanel 원본의 명성 텍스트 참조는0이지만 GameUI가 실제 텍스트 참조로 덮어쓴다. 판매 통계·매출·잔액·벌금은 Presenter 참조가 연결돼 있다. 이는 소스/직렬화 확인이며 실제 화면에서의 가독성·누락 여부는 이번 사람이 하는 테스트에서 확인한다.

마감 이후 계산대의 마지막 거래를 완료할 수 있다. 정산 Sales에는 이 거래도 들어갈 수 있으므로, `마감 뒤 마지막 거래 있음`인 날의 Sales를 곧바로180초 안에 끝낸 건수로 해석하지 않는다. 가격 제출과 결과 확인이 마감을 사이에 두고 나뉠 수도 있어 임의로1건을 빼지도 않는다. 일시정지·에디터 중단·외부 도움을 사용한 날도 따로 표시한다.

## 기록을 받은 뒤 계산할 항목

- 일 평균 성립 수 = Sales 합계 ÷ 기록한 영업일 수. 정상 종료한0건 날도 분모에 포함한다.1일차의 학습 효과를 보기 위해 전체1~3일과2~3일을 나눠 보고,3일만으로 안정적인 평균을 확정하지 않는다.
- 일 평균 매출과 평균 객단가 = 각각 매출 합계 ÷ 영업일 수, 매출 합계 ÷ Sales 합계. Sales 합계0이면 객단가는 계산 불가다.
- 거절 비율 = Refused 합계 ÷ (Sales+Refused) 합계. 대기 이탈은 별도 평균으로 보고, 생성 수가 없으므로 정확한 이탈률로 바꾸지 않는다.
- 시간 조건이 같은 날끼리8/10/12건의 기준과 비교한다. 마감 초과·중단·정가 이외 거래가 있으면 시민권 모형과 직접 일치하는 실행으로 분류하지 않는다.

| 기존 처리량 가정 | 180초의 평균 거래 주기 | 명목 자동 연출4.15초를 뺀 시간 |
|---|---:|---:|
| 8건 | 22.5초 | 18.35초 |
| 10건 | 18초 | 13.85초 |
| 12건 | 15초 | 10.85초 |

표의 시간은 입력·계산·결과 확인에 쓸 수 있는 이론상 예산이며 실측 처리 시간이나 합격선이 아니다. 속도가 부족하면 처음부터 상품 가격을 올리기보다 조작·계산·결과 확인 중 어디에서 시간이 걸리는지 기록과 함께 검토한다. 명성 문구가 정체돼도 곧바로 거래 실수로 단정하지 않는다. 현행 큐의 성급한 손님 이탈과 정산 점수 경계도 원인일 수 있다.

## 이후 구간에서 추가할 내용

초반 결과를 검토한 뒤 자연 진행으로10~13일,20~23일 구간을 본다. 같은 기록표에 실제 가게 단계·활성 상품설비·구매일을 덧붙이고, 구매 다음날부터 상품 후보가 늘었는지 살핀다. 설비가 활성화돼도 일일 상품 추첨에서 빠질 수 있어 하루에 새 상품이 보이지 않는다는 이유만으로 해금 실패로 판단하지 않는다.

가게 단계의 목표는1/10/20일, 대표 상품설비의 구매 목표는3/12/22일이고 상품 활성은다음날이다. 모형의 전체 투자 순서와 다른 선택을 했다면 그대로 기록하고 같은 선택의 계산과 비교한다. 목표 날짜에 맞추려고 잔액·구매 조건을 바꾸지 않는다. 장기 플레이를 실제로 완료한 뒤에만31일 자금과 시민권100만G 분석을 비교한다.

사람의 실제 입력과 측정은 아직 `미실행`이다. 이번 작업은 기록표와 코드상 표시 항목의 대조까지 완료한 `PARTIAL`이며 게임 데이터·UI·설정을 변경하거나 테스트 결과를 대신 채우지 않았다. 기획 역할의 완료 상태만 확인되고 회신 본문은 없으므로 역할 리뷰 승인으로 집계하지 않았다.
